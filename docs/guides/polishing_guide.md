# CRM + RAG — Days 11–13 Roadmap

### Finishing Day 10, then high-leverage improvements given the interview postponement

> Context: Full stack deployed on Render (Postgres+pgvector, API, frontend), keep-alive cron in place. Interview postponed to next week, exact day unknown. This plan is sequenced so that if the interview happens sooner than expected, the most valuable work is already done — finish committed deliverables first, then layer on genuinely high-leverage improvements, roughly in descending order of value.

---

## Guiding principle for these extra days

Resist the temptation to keep adding features indefinitely just because there's more time. The goal was never "build the most features" — it was "demonstrate you can reason about RAG architecture and ship a working, well-tested, explainable system." Every day below should either (a) close a real gap you already know about, or (b) deepen your ability to explain a tradeoff you made. Anything else is scope creep.

## Day 12 — Close the known gaps (8h)

Every item here is something you already identified as a real limitation this week — closing them is higher leverage than adding anything new, since you can already speak to exactly why they matter.

| Hours | Task                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 88–89 | **Feed structured deal fields into AI context.** In `AiService.chat()`, when `dealId` is provided, fetch the deal record (you already have `DealsService.findOne`) and prepend its `title`, `value`, `status`, `stageId`→stage name to the prompt context alongside retrieved notes. Closes the gap where "What's the deal value?" required inference from note text instead of reading the actual field                 |
| 89–90 | **Re-embed on activity update.** `ActivitiesService.update()` currently doesn't touch `activity_chunks` when `body` changes. Add: delete existing chunks for that activity, re-run `embedActivityBody()` if the new body is provided. Small, contained fix, closes a real correctness gap                                                                                                                                |
| 90–91 | **Formalize the `/ai/chat` integration test** (deferred from Day 7). Seed a known activity, ask a question only answerable from it, assert the response cites the right source and contains expected key terms                                                                                                                                                                                                           |
| 91–93 | **Latency optimization on the Gemini call** (the measured 5.7s bottleneck). Two options, pick one: (a) switch the `/ai/chat` endpoint to Gemini's streaming API so the UI shows tokens as they arrive instead of one 5.7s wait — better UX, more implementation work; (b) try `gemini-flash-lite` for a quality/speed tradeoff comparison, document the difference. Given time available, (a) is more impressive to demo |
| 93–94 | **Rate limiting on auth endpoints.** `/auth/login` and `/auth/signup` currently have no brute-force protection. Add `@nestjs/throttler` — a few lines of config, closes a real security gap that would come up in any serious code review                                                                                                                                                                                |
| 94–95 | **Input sanitization audit.** Confirm `class-validator`'s `whitelist`/`forbidNonWhitelisted` is applied to every remaining DTO (run the `grep -rL "class-validator"` sweep from Day 6 one more time — new DTOs may have been added since)                                                                                                                                                                                |

## If the interview call comes before you finish Day 12 or 13

Stop wherever you are — Day 11 alone brings you back to a fully demo-ready, documented state. Everything in Days 12–13 is additive polish on top of an already-complete project, not a blocker. Check the README's limitations section is current before the call, since that's your fallback talking-points list regardless of how far you got.

## Talking points this extra work adds, if completed

- **CI pipeline**: "I set up automated testing on every push, not just local runs" — a real engineering-maturity signal
- **Streaming responses**: "I measured the latency, found the bottleneck was generation, and fixed the _perceived_ latency with streaming rather than chasing a marginal model swap"
- **Structured + unstructured context fusion**: "The AI doesn't just search notes — it also reads the actual deal record, so answers about hard facts (value, status) are grounded in truth, not inference"
- **Re-embedding on edit**: "I noticed a data-freshness bug during my own testing and fixed it before it became a real problem" — good story about your own QA discipline
- **Gist + short demo clip**: a fast, low-friction way to share the project outside a formal interview setting (a recruiter, a Slack message, a LinkedIn post) — deliberately swapped in ahead of hybrid search after a colleague's review, which is itself a small example of taking outside feedback and re-prioritizing quickly
